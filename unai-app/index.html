?How this works — in one sentence

      
Imagine a task that normally needs 4 separate specialist agents. Each one would have to be built to read your systems, keep its own memory, make decisions, and message the others — the same plumbing, four times over. A UNAI is one worker that already owns that plumbing (the 7 shared layers) and just picks up a tiny playbook (tool pack) for each task. So one agent does the job of four — and you only built the hard 90% once.

Benefits of UNAIs

    
The payoff of building the seven layers once. Run the demo on the Build & Run tab to replace the projections with measured numbers.

    

      
?Why one agent is so much cheaper than many

      
If 10 agents each rebuild 7 layers, that's 70 builds to write, test, secure and maintain — and every time agents must talk, you wire another connection (10 agents = 45 wires). With a UNAI you build 7 layers once and add a small playbook per job, and agents coordinate over one shared bus instead of point-to-point wiring. Less to build, far less to maintain, and each new use case is a configuration — not a project. The cards below quantify that; the run-linked ones update each time you execute.

    

    

  







  

    
ROI — what it costs vs what it saves

    
The business case for collapsing many specialist agents into one UNAI: build cost, annual run & maintenance, model/inference spend, and onboarding — Gen-1 versus UNAI — plus the payback point and 3-year savings. Adjust the assumptions and every number and chart updates live.

    

      
?Where the savings come from (and what's modeled)

      
You build the seven layers once instead of inside every agent, so build and maintenance scale with tool packs, not agents. One shared memory + one ontology cut redundant model/inference spend, and a new system or capability is a configuration, not a project. Pricing decomposable

    
A transparent, value-based model you can see the build-up of: a platform base + capability packs + connectors + autonomy usage. The T-shirt tiers are just presets of these line items. Edit any assumption and the total, the tier and the value anchor update live.

    

      
?Why this model (not T-shirt sizing alone)

      
T-shirt tiers are easy to buy but hide how you got the number; pure usage pricing is transparent but unpredictable. This hybrid keeps both: charge on capabilities (tool packs) in production — the thing that grows with customer value — never per agent (which would penalize the whole "many→one" thesis). Land with one use case, expand as packs are added. Price is anchored to a fraction of the savings the ROI model computes.

    

    

      
📦What a capability pack includes (the unit you price)

      
A capability pack (aka a "pod") is one business capability in production — e.g. Supplier Disruption, Spares Planning, or RMA Execution. It is the "recipe" that reuses the shared kitchen; buying one gives the customer:

      
• The capability itself — the domain tool-pack logic (the only custom code) that delivers that outcome.

      • Its canonical-ontology mappings — so it reads your systems (SAP / Databricks / Snowflake / ServiceNow / OSS) with zero re-mapping.

      • Governance config — autonomy threshold, value/approval gate and guardrails for that capability.

      • Full use of the seven shared layers — perception, memory, reasoning, evidence, action, collaboration, explainability — plus unified observability & one audit trail.

      • Runs on the shared runtime, deployable in-tenant on any cloud, with export/deploy.

      
What a pack is NOT: it is not a new agent and it does not rebuild the seven layers (those are built once and shared). That's exactly why the 4th pack costs far less to add than the 1st — and why price grows slowly (taper) as packs are added.

Gen-1 (many agents) vs UNAI (one agent) — same job, measured

    
A side-by-side of the run & observability metrics for the same use case built two ways: the classic Generation-1 pattern (a specialist agent per capability) versus Generation-2 UNAI (one agent, seven shared layers). UNAI numbers are measured from your last run; Gen-1 numbers are modeled from the same workload with transparent assumptions.

    

      
?How to read this — why the two columns differ

      
Both architectures do the identical business work and touch the same systems. The difference is structural overhead: Gen-1 rebuilds the seven layers inside every agent, re-maps each system's schema on every hop, re-loads context per agent, and wires agents point-to-point — so cost grows with the number of agents. UNAI builds the seven layers once, maps each system once into the canonical ontology, shares one memory + one telemetry surface, and coordinates over one bus. Each row below shows the metric, both values, the delta, and the mechanism that causes it.

    

    

      
🍽The mental model — food trucks vs one restaurant

      
Gen-1 = 12 food trucks. Each truck has its own kitchen, fridge, staff and till (7 subsystems each) → 84 subsystems to build, staff and run.

      
UNAI = 1 restaurant. One shared kitchen, fridge, staff and till (7) + 12 recipes (the tool packs) → 19 things to run. A recipe reuses the kitchen — it isn't a whole new kitchen. That's why adding a dish costs +1 recipe, not +7 subsystems.

    

    

      
≠How UNAI differs from an orchestrator or MCP — and why it's unique

      
Multi-agent orchestrator (LangGraph, CrewAI, AutoGen): you still have N separate agents; a conductor routes tasks between them. Each agent still owns its own seven layers, so the duplication and the N² coordination are still there — orchestration manages the sprawl, it doesn't remove it. UNAI removes the agents: one substrate, capabilities added as tool packs.

      
MCP (Model Context Protocol): a universal cable to connect a model to tools and data sources. It standardizes transport — how you reach a system — but not meaning: each client still interprets every source's schema itself, and MCP gives you no shared memory, evidence, governance or explainability. MCP moves data; it doesn't reconcile it. UNAI is complementary — it can use MCP as its Perception/Action transport, then the canonical ontology adds the shared meaning (MATNR = sku, everywhere) so switching systems costs zero re-mapping.

      
What makes UNAI unique: (1) the substitution principle — 7 layers built once + one small tool pack per capability; (2) a canonical ontology that gives semantic zero-re-map interoperability (neither orchestrators nor MCP provide this); (3) accountable autonomy — every decision carries confidence, attribution and a uniform value/confidence gate; (4) one observability + audit surface; (5) open-weight, self-hostable model portability. In short: an orchestrator conducts many agents, MCP is the cable to tools — UNAI is the single agent + shared meaning that can sit on top of both.

Connections — configure your data sources

    
Point UNAI at your lakehouse. Configure Databricks and Snowflake here; both plug in through the same adapter and canonical ontology, so use cases run unchanged on either. Non-secret settings are entered here; the token/password is set as an environment variable in your shell — never typed into or stored by the app.

    

      
?Why credentials go in the environment

      
UNAI reads the secret (PAT / password / key) from an environment variable at runtime, so it never lives in the UI, a config file, or the browser. You fill the non-secret connection details below, copy the generated env block, set the secret in your shell, restart the server, and the status turns green. This is the same 12-factor pattern that makes the agent portable across clouds.

Agent Foundry add-on

    
Let developers and business users put agents onto the UNAI substrate — either build a new one here, or submit an existing agentic app and convert it into a UNAI agent. Both paths produce one governed, runnable Agent Manifest (agent-as-configuration) on the seven shared layers.

    

      
?How the Foundry works

      
Behaviour lives in a declarative manifest — capabilities (tool packs) + system mappings through the canonical ontology + governance — executed by the shared runtime, never as new agent code. Build composes a manifest from a catalog. Convert ingests an existing agent spec (LangGraph, CrewAI, AutoGen, an MCP tool list, or an OpenAI Assistant), analyses it against the seven layers, maps its tools/data through the ontology, and emits a manifest plus a Conversion Report that quantifies what was absorbed into the shared layers and the Gen-1→UNAI compression it buys. Conversion is assisted and review-gated — unsupported constructs are surfaced for a human, never silently dropped.
